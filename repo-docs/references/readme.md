# README

The README is the front door. A reader should learn within a minute what the repo is, whether it is what they need, and how to get it running.

## Questions it answers, in this order

1. **What is this?** One or two sentences under the title, in plain words, saying what it does and for whom. No badges or history before it.
2. **How do I get it running?** The shortest path from clone to working: prerequisites with versions, install, and one command that shows it working. Every command is copyable and was checked against the repo.
3. **How do I use it?** The most common use, as a real example with its expected result. Link out for the rest.
4. **How is it configured?** The settings a user must or will probably change. Link to the full reference if one exists.
5. **Where is everything else?** Links to CONTRIBUTING, the changelog, architecture, decisions, and runbooks, as they exist.
6. **Who owns it, and under what licence?** The team or contact for an internal repo; the licence for a public one.

Leave out a section that has nothing to say.

## By repo type

- **Library**: install from the package index, a minimal import-and-call example, supported language and runtime versions, a link to the API docs.
- **Service**: what it does within the wider system, how to run it locally, its required configuration and dependencies (databases, queues, other services), how it's deployed, and links to runbooks and dashboards.
- **CLI tool**: install, the two or three most used commands with output, and how to get help (`--help`). Don't copy the full help text; it will drift.
- **Terraform module**: what it creates, a minimal `module` block that works, provider and Terraform version requirements, and the inputs and outputs. If the inputs/outputs table sits between `<!-- BEGIN_TF_DOCS -->` markers it is generated by `terraform-docs`; never edit it by hand. Fix the `description`s in the `.tf` files and regenerate.
- **Infrastructure/live config**: what environments and accounts it manages, how changes are planned and applied (and by whom or what), and the layout of the tree.
- **Internal tool or script collection**: a table of what's there with a line each, and how to run one.

## Writing it

- Keep the README short enough to scan. When a section grows past a screen, move it to `docs/` and link to it.
- Take commands from the manifests, Makefile, and CI config, not from memory of what such projects usually use.
- Prefer one working example to a description of what is possible.
- Use relative links for files in the repo.
- Badges are optional. Keep only the ones that tell a reader something (build status, published version), and put them after the opening sentences or follow the repo's habit.

## Common findings

- No statement of what the project is.
- Setup steps that fail: a wrong command, a missing prerequisite, an undocumented environment variable. Compare with CI, which shows the steps that really work.
- Examples using flags, arguments, or variables that have been renamed or removed.
- Content duplicated from CONTRIBUTING or the docs directory, with the copies out of step.
- Template leftovers: placeholder text, empty sections, "TODO: describe".
- Dead links and links to moved files.
- A long list of features where one example would show more.
